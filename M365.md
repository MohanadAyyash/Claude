# الربط مع Microsoft 365 — المرحلة الأولى / Microsoft 365 link — Phase 1

يربط **مدير النظام** حسابه في النظام بحسابه في Microsoft 365 (Entra ID) عبر OAuth 2.0 Authorization Code + PKCE.
الربط يتم بعد الدخول بكلمة المرور. المرحلة 1B (في آخر الملف) تضيف الدخول باستخدام Microsoft للحسابات المربوطة فقط؛ الدخول بكلمة المرور يبقى.

**Each ERP user** (Phase 1C; administrators only before) links their own ERP account to their Microsoft 365 (Entra ID) account with OAuth 2.0 Authorization Code + PKCE.
The link is made after the normal password sign-in. Phase 1B (end of this file) adds *sign in with Microsoft* for linked accounts only; the password sign-in stays.

## 1. App registration (Microsoft Entra admin center)
1. **App registrations → New registration**: single tenant ("Accounts in this organizational directory only").
2. **Redirect URI** (platform *Web*): exactly `https://erp.trigon.ae/auth/microsoft/callback`.
3. **Certificates & secrets → New client secret**: copy its **Value** (not the ID).
4. **API permissions → Microsoft Graph → Delegated**: `openid`, `profile`, `email`, `offline_access`, `User.Read` — nothing else in Phase 1.

## 2. The runtime dependency (installed by the update)
`jose` verifies Microsoft's signed sign-in answer (pinned in `package-lock.json`).
- **Office PC:** `Trigon-Update.bat` runs `npm ci --omit=dev --ignore-scripts` in a staging copy, checks it, and only then swaps the
  program files and `node_modules` in. If the install fails, nothing is changed; if anything fails after the stop, the previous version
  is restored and restarted. Exit code 1 in both cases. See [UPDATE.md](UPDATE.md), including the **one-time bootstrap** of the
  updater on the office PC (the current one cannot replace itself) and the Windows test procedure.
- **Updating by hand** (copying the files from the ZIP): run `npm ci --omit=dev` in the system folder afterwards.
- **Docker:** the image must run `npm ci --omit=dev` (the current `Dockerfile` does not; add it before enabling the link there).
- **Standalone (browser) edition:** has no Microsoft 365 link at all (it cannot keep a client secret or receive the callback);
  `jose` is not bundled and Settings says the link is not available there.

If `jose` is missing anyway, the ERP still starts and the link stays closed (Settings lists `jose` as missing). That is an emergency
safety behaviour, not a supported way to run: run `npm ci --omit=dev`.

## 3. Server settings (`.env` next to `server.js`, never in git or the database)
```env
M365_ENABLED=1
M365_TENANT_ID=<Directory (tenant) ID>
M365_CLIENT_ID=<Application (client) ID>
M365_CLIENT_SECRET=<client secret Value>
M365_REDIRECT_URI=https://erp.trigon.ae/auth/microsoft/callback
M365_ENCRYPTION_KEY=<32 random bytes, base64>
```
Generate the encryption key once: `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`.
Keep it only in `.env`. If it is lost or changed, disconnect and connect again. Restart the system after editing `.env`.

If `M365_ENABLED=1` but a value is missing or invalid, the link stays closed and **Settings → Microsoft 365 link** lists which setting is missing (never its value).

## 4. Use (every user, own account)
**Settings → Microsoft 365 link → Connect Microsoft account** → sign in at Microsoft → back in Settings, "Linked to …".
**Check the link** calls Microsoft Graph `/me`.
**Remove the link from Trigon ERP** deletes the link and its tokens from Trigon ERP only. It does **not** revoke anything at Microsoft:
the user's consent to the app (and any Microsoft sessions) stays until it is removed in the Microsoft account (*My Apps → Manage your applications*)
or by an Entra administrator (*Enterprise applications → the app → Users and groups / Permissions*). Phase 1 has no permission to revoke it from the ERP.

One Microsoft account (tenant + object ID) can be linked to **one** ERP user only. The email and name are shown for information; the
link is keyed by the account's object ID, so a changed email does not create a new identity. Linked users who are deleted, disabled or
lose their link automatically (Phase 1C: a role change keeps it).

The sign-in answer (id_token) is checked with the `jose` library against the tenant's published signing keys
(`https://login.microsoftonline.com/<tenant>/discovery/v2.0/keys`): RS256 only, issuer `https://login.microsoftonline.com/<tenant>/v2.0`,
audience = client ID, tenant, nonce, expiry. If the keys cannot be fetched the link is refused.

## What is stored, and where
| Item | Where | How |
|---|---|---|
| Client secret, encryption key | `.env` only | never in the database, the browser, responses or logs |
| Access / refresh tokens | `m365_connections` | AES-256-GCM with `M365_ENCRYPTION_KEY` |
| OAuth state | `oauth_states` | SHA-256 hash only, single use, 10 minutes, deleted when the callback finishes; expired / used rows cleaned up |
| PKCE verifier | `oauth_states` | AES-256-GCM |
| Backups (download, automatic, `scripts/backup.js`) | — | always through `lib/backupsafe.js`: tokens and sign-in states removed from the copy, VACUUM, `PRAGMA integrity_check`, file mode 0600; on any failure the copy is deleted and the previous backup is kept |

Audit log (`m365`): `config-change`, `connect`, `connect-failed`, `refresh-failed`, `disconnect`.

## Switching it off / rollback
Set `M365_ENABLED=0` (or remove the `M365_*` lines) and restart: the routes answer "off" and nothing calls Microsoft.
The two tables are additive and unused when off; they can stay. Also remove the app's consent in Entra if the link should be revoked there.

## Manual smoke test on the real tenant (before go-live; not automated)
Use a **test app registration** first. Never put real credentials in tests, tickets, chat or screenshots.

1. `.env` on the server only: `M365_ENABLED=1`, the tenant GUID in `M365_TENANT_ID` (not `common` / `organizations`), the app's
   `M365_CLIENT_ID`, the client secret **Value** in `M365_CLIENT_SECRET`, a new 32-byte `M365_ENCRYPTION_KEY`, and
   `M365_REDIRECT_URI` exactly as registered in Entra (`https://erp.trigon.ae/auth/microsoft/callback`). Restart the system.
2. **Settings → Microsoft 365 link** shows the card with no "missing" line (jose installed, configuration complete).
3. Signed in as an administrator, open the system at `https://erp.trigon.ae` (the registered host) and press **Connect Microsoft account**.
4. Microsoft shows the consent screen with only: sign you in / read your profile / maintain access (offline). Accept.
5. Back in Settings: "Linked to <your Microsoft email>". In the audit log: `connect` with the account's object ID.
6. Compare that object ID with the user's **Object ID** in Entra (Users → the user) — they must match.
7. **Check the link** → shows your email (Graph `/me` works).
8. Refresh path (where practical): wait about an hour, or stop the server and set that user's `expires_at` in the past on a **test copy**
   only, then **Check the link** again → still works (a refresh happened; no `refresh-failed` in the audit log).
9. `GET /api/m365/status` (browser dev tools) shows only IDs, booleans and your link — no secret, key or token.
10. **Remove the link from Trigon ERP** → the card shows "Not linked"; the audit log says "Microsoft consent not revoked". In Microsoft
    *My Apps*, the app's consent is still listed (expected); remove it there if wanted.
11. Logs: search the server console / `data` error log for the client secret, `eyJ` (the start of a token) and the encryption key → nothing.
12. **Settings → Back up now** and **Download backup**; open the copy with any SQLite tool: `m365_connections` token columns are empty and
    `oauth_states` is empty.
13. Switch `M365_ENABLED=0`, restart: the card disappears and `/auth/microsoft` answers "off".

# المرحلة 1B: الدخول باستخدام Microsoft / Phase 1B: sign in with Microsoft (Entra SSO)

**بالعربي باختصار:** زر «تسجيل الدخول باستخدام Microsoft» في صفحة الدخول. Microsoft تتحقق من الهوية (ومن MFA حسب سياسة المؤسسة)،
والنظام يفتح **فقط** حساباً موجوداً، نشطاً، ومربوطاً مسبقاً بنفس حساب Microsoft (المستأجر + معرّف الكائن oid)، بدوره وصلاحياته
الحالية. لا يُنشأ أي حساب، ولا مطابقة بالبريد. الدخول بكلمة المرور يبقى كما هو.

## Setup (one step in Entra, nothing new in `.env`)
In the **same** app registration: *Authentication → Web → Redirect URIs → Add*:
`https://erp.trigon.ae/auth/microsoft/login/callback` (keep the existing `…/auth/microsoft/callback`). No new permission, no new secret:
sign-in asks only `openid profile email User.Read` and stores no Microsoft token. The sign-in redirect URI is derived from
`M365_REDIRECT_URI` (same origin + `/auth/microsoft/login/callback`). The button appears when the link is enabled and configured.

## Flow
`/auth/microsoft/login` (no ERP session needed) → Microsoft (tenant endpoint, PKCE S256, state, nonce) → `/auth/microsoft/login/callback`:
1. state: SHA-256 hash in `oauth_login_states`, bound to this browser (`m365_login` cookie: HttpOnly, SameSite=Lax, path
   `/auth/microsoft/login`, 10 minutes), single use (marked used, then deleted, whatever the outcome);
2. code + PKCE verifier exchanged at the tenant token endpoint;
3. id_token verified exactly as in Phase 1 (jose, tenant JWKS, RS256, issuer, audience, tenant, `oid`, expiry) with a **sign-in nonce**
   that differs from the link flow's, so a token or state from one flow is never accepted by the other;
4. Graph `/me` must name the same object ID (the access token is used once and not stored);
5. the link is looked up by **(configured tenant, object ID) only**, never by e-mail, UPN or name; then the ERP user: it must exist, be
   active (any role since Phase 1C);
6. a new ERP session exactly like the password login (`createSession`, same `sid` cookie: HttpOnly, SameSite=Strict, Secure behind
   HTTPS, 30 days); a session the browser presented is ended first (no fixation); redirect to `/` (no code or token in the address).

Every refusal is a dead end with a page that links back to the sign-in page; nothing falls back to e-mail and no session is created.

## Decisions for review
- **Who can sign in with Microsoft** *(superseded by Phase 1C below: every active user)*: only users who can have a link. In Phase 1 that is **administrators** (they link their own account
  while signed in with their password; links of users who are disabled, deleted or no longer administrators are removed). Letting other
  roles link (and so use Microsoft sign-in) is a separate, later change.
- **The ERP's own two-step code is not asked** after a Microsoft sign-in (MFA belongs to Entra). Before go-live, make sure a Conditional
  Access policy **requires MFA** for this app (Entra → Conditional Access → target the app). The password sign-in still asks the ERP code.
- **Break-glass:** the password sign-in is unchanged and not switchable in this PR. A later "Microsoft only" mode should keep at least one
  dedicated local administrator (strong password + ERP two-step), default off, and refuse to switch on unless such an account exists.
- **Rate limit:** anyone can start a sign-in, so starts are limited to 20 per address per 10 minutes and 1000 pending states.

Audit log (`m365`): `login` (user, Microsoft object ID), `login-rejected` with the reason (not linked; ERP user disabled / no longer exists /
Microsoft identity not verified + Microsoft's error code; state used twice / expired; Microsoft returned an error).
An unknown state is not audited (anyone can send one). Never logged: codes, tokens, client secret, encryption key, PKCE verifier.

Rollback: remove the `…/login/callback` redirect URI in Entra, or `M365_ENABLED=0` (switches off the link too), or revert the PR. The
`oauth_login_states` table is additive and can stay.

# المرحلة 1C: كل المستخدمين / Phase 1C: Microsoft sign-in for every existing ERP user

**بالعربي باختصار:** كل مستخدم نشط في النظام (أي دور) يربط **حسابه هو فقط** من الإعدادات ← «حساب Microsoft 365» وهو داخل بكلمة
المرور، ثم يستطيع الدخول بزر Microsoft. الدور والصلاحيات والمشاريع تبقى كما هي في النظام تماماً؛ لا يُقرأ أي شيء من Microsoft
(أدوار، مجموعات، مسمى وظيفي) لتحديد الصلاحيات. لا يُنشأ أي مستخدم، والمطابقة بـ tenant + oid فقط. الدخول بكلمة المرور يبقى للجميع.

## Access control (exact)
| What | Who | How it is enforced |
|---|---|---|
| `GET /api/m365/status` | any signed-in user | own link only (`me.id`). Non-admins get `{available, enabled, configured, connection:{email, display_name, linked_at}}` — no tenant / client / object IDs, no server settings. Administrators also get the configuration summary (no secret values). |
| `POST /api/m365/disconnect` | any signed-in user | deletes the caller's own row (`WHERE user_id = me.id`) with its encrypted tokens, and its pending link states; audited `disconnect` |
| `POST /api/m365/check` | any signed-in user | Graph `/me` with the caller's own link |
| `GET /auth/microsoft` (link start) | any signed-in, active user | the state row stores `me.id` from the session; **no request parameter is read for the user**. The callback links to the user who started the flow, in the browser that started it (binding cookie). |
| link callback | — | user still active; Microsoft identity verified (tenant JWKS, tid, oid, nonce, Graph id == oid); identity not linked to another user (check + unique index `(tenant_id, microsoft_user_id)`); one row per ERP user (`user_id UNIQUE`: linking another account replaces the old one) |
| `GET /auth/microsoft/login` + callback | anyone (signed out) | ERP user found by `(configured tenant, oid)` only; must exist and be active; session = the password login's `createSession(user.id)` |
| everything else | the ERP | `sessionUser()` re-reads role and disabled on every request; `lib/acl.js` and project scoping unchanged. Nothing from Microsoft (roles, groups, `wids`, job title, e-mail) is used for authorisation. |
| users list (`GET /api/users`) | administrators (and HR for employee accounts, as before) | `m365_linked` yes/no only, no IDs |

`lib/acl.js`: `m365` moved from admin-only to self-service (like `password` / `2fa`), including the `employee` role.
`prune()`: links are removed for deleted or disabled users (no longer for non-admins); a role change keeps the link.

## Break-glass administrator (design for the later "Microsoft only" switch — not implemented)
- One dedicated local account (e.g. `breakglass`), role `admin`, long random password kept offline (sealed envelope / safe), ERP two-step
  on, never linked to Microsoft, not used day to day; its sign-ins are audited and reviewed.
- The later switch (e.g. `ERP_LOCAL_LOGIN=breakglass-only`) would refuse password sign-in for every other account **only after** checking
  that a break-glass account exists, is active, is an administrator and has two-step on; default = current behaviour (password for all).
- It needs no Entra, Graph or internet: the password path is entirely local (also over the LAN / on the server PC).
- No hidden bypass: it is a normal account, visible in Users, with the normal password + two-step check.

# الدخول عبر Microsoft أولاً / Microsoft-first authentication

**بالعربي باختصار:** `AUTH_MODE=microsoft-first` يجعل «تسجيل الدخول باستخدام Microsoft» الطريقة الوحيدة لدخول الموظفين، ويُخفي نموذج
كلمة المرور ويُغلقه على الخادم للجميع. يبقى مسؤول طوارئ محلي واحد على الأقل (`AUTH_EMERGENCY_ADMINS`) يدخل من `/auth/emergency` بكلمة
المرور + رمز التحقق بخطوتين، بدون Microsoft أو إنترنت. لا يتفعل الوضع إلا إذا كان مسؤول الطوارئ صالحاً، وإلا يبقى «مختلط» ويذكر السبب.

## Settings (`.env`)
| Variable | Values | Meaning |
|---|---|---|
| `AUTH_MODE` | `hybrid` (default) / `microsoft-first` | anything else = hybrid (and the reason is shown) |
| `AUTH_EMERGENCY_ADMINS` | usernames, comma-separated | the break-glass accounts; usernames only, no secret |
| `AUTH_EMERGENCY_SESSION_MINUTES` | default **60**, allowed 5–240 | emergency session length; not a positive number → 60, more than 240 → 240 |
| `AUTH_MICROSOFT_SESSION_HOURS` | default **12**, allowed 1–720 | Microsoft session length; not a positive number → 12, more than 720 (the ERP's 30-day limit) → 720 |
| `M365_*` | as above | unchanged |

**Effective mode** = `microsoft-first` only if requested **and** Microsoft sign-in is enabled + configured **and** at least one emergency
account is valid: it exists, role `admin`, active, ERP two-step on, **not** linked to Microsoft. Otherwise `hybrid`, with the reason in
Settings → Microsoft 365 account (administrators) and `/api/m365/status` → `auth`. Every change of the effective mode is audited
(`auth` / `auth-mode`); entering microsoft-first **ends every password session** (audited with the count), and switching back does not revive them.

## Architecture
| Way in | Path | Who | Session (`sessions.method`) |
|---|---|---|---|
| Microsoft | `/auth/microsoft/login` → Entra (MFA / Conditional Access) → `/auth/microsoft/login/callback` | any linked, active user | `microsoft`, **12 hours** (default) |
| Password form | `POST /api/login` | **hybrid only**; in microsoft-first: 403 for everyone, before the password is checked | `password`, 30 days |
| Emergency | `GET`/`POST /auth/emergency` (own page, not the app) | users named in `AUTH_EMERGENCY_ADMINS` who are admin, active, with the ERP code on | `emergency`, **60 minutes** (default, at most 4 hours) |

- One session framework: every way in uses `createSession(user, method)` and the same `sid` cookie (HttpOnly, SameSite=Strict, Secure
  behind HTTPS); a session the browser presented is ended first (no fixation); redirects go to `/` (no code or token in the address).
- In microsoft-first, `sessionUser()` accepts only `microsoft` and `emergency` sessions.

## Session lifetimes and Entra sign-in frequency
- Every ERP session lasts a fixed time **from when it was created**; using it never extends it (no sliding expiry), and the cookie's
  Max-Age matches. A new sign-in (password, Microsoft or emergency) always makes a **new** session with its own method and lifetime; a
  Microsoft or emergency sign-in also ends the session the browser presented, so nothing can extend an emergency session.
- **Password:** 30 days (unchanged; hybrid only). **Microsoft:** 12 hours by default (`AUTH_MICROSOFT_SESSION_HOURS`), so the office
  signs in once a working day. **Emergency:** 60 minutes by default (`AUTH_EMERGENCY_SESSION_MINUTES`, at most 4 hours).
- **How it combines with Entra.** The ERP session is the ERP's own; Microsoft is asked again only when it ends. When it ends, the
  user presses *Sign in with Microsoft*: if the Microsoft (browser) session is still valid under the Conditional Access policy, Entra
  answers without a prompt; if the policy's **sign-in frequency** has passed, Entra asks for the password / MFA again. So:
  - effective re-authentication with Microsoft ≈ **every ERP session (12 h)**, and MFA ≈ every **max(ERP session, CA sign-in frequency)**;
  - an Entra sign-in frequency **shorter** than 12 h does **not** cut an ERP session already running (the ERP does not ask Microsoft
    during a session); set `AUTH_MICROSOFT_SESSION_HOURS` to the same value if it must;
  - disabling a user **in Entra** stops their *next* Microsoft sign-in, not a running ERP session. To cut access at once, disable
    the user **in the ERP** (or Disconnect their link): `sessionUser()` checks the ERP user on every request.
- Recommended for Trigon: Conditional Access **require MFA** + **sign-in frequency 12 hours** for this app, `AUTH_MICROSOFT_SESSION_HOURS=12`
  (default), `AUTH_EMERGENCY_SESSION_MINUTES=60` (default).
- Authorisation is unchanged: role, ACL, project scope and disabled state come from the ERP on every request. Entra claims (`roles`,
  `groups`, `wids`, job title, e-mail) are never used for it.
- Identity: (configured tenant, verified `oid`) → `m365_connections` → active ERP user. No e-mail / UPN / name fallback, no auto-provisioning.
- Link (onboarding): an active user links their own account while signed in (password in hybrid, or Microsoft / emergency session).
  New employees: link them while in hybrid, or switch to hybrid for onboarding and back.

**Emergency sign-in (`/auth/emergency`)**: password **and** the current ERP code (TOTP, single use) of a named, active administrator;
POST only from this site's own page (Origin check); 5 attempts per 15 minutes per address **and** per account (also counting successes);
the same answer for every refusal (no account probing); every attempt audited (`auth` / `emergency-login`, `emergency-login-failed` with
the reason and address, never the password or code). Its security is authentication + authorisation + limits + audit, not a hidden URL.

## Break-glass administrator: production set-up
1. In hybrid, create a dedicated user (e.g. `breakglass`), role **Administrator**, a long random password (25+ characters).
2. Sign in as it once (password) → Settings → **Two-step sign-in** → switch on (an authenticator on a phone kept by the owner / in the
   safe; note the setup key in the sealed envelope too). Do **not** link it to Microsoft.
3. Keep the password and the setup key offline (sealed envelope in the safe). Two people should know where.
4. `.env`: `AUTH_EMERGENCY_ADMINS=breakglass` (two accounts are better than one). Restart (procedure below).
5. Test `/auth/emergency` once; Settings shows "Emergency administrators: breakglass ✔".
6. Review the audit log (`emergency-login…`) monthly; any use outside an incident is investigated.

## Entra changes
- Redirect URIs (Web) of the app: `…/auth/microsoft/callback` **and** `…/auth/microsoft/login/callback` (already done for 1B).
- **Conditional Access**: a policy that requires MFA for this app (Entra → Protection → Conditional Access → target the app, all users,
  grant: require MFA). The ERP does not check MFA itself; it trusts only a verified Entra sign-in.
- No new API permission (still `openid profile email offline_access User.Read`). No new secret.

## Restart that really applies `.env` (office PC)
`.env` is read once, when `node server.js` starts. Stopping the scheduled task does not always end its `node.exe`, so check it:
```powershell
$before = Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '*server.js*' } | Select-Object ProcessId, CreationDate
Stop-ScheduledTask TrigonERP
Get-NetTCPConnection -LocalPort 3000 -State Listen -ErrorAction SilentlyContinue | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
Start-ScheduledTask TrigonERP; Start-Sleep 5
$after = Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '*server.js*' } | Select-Object ProcessId, CreationDate
$before; $after                                   # the ProcessId must be new and the CreationDate after the .env change
(Invoke-WebRequest -UseBasicParsing http://localhost:3000/api/status).Content   # auth_mode / m365_login show the new settings
```
Settings → Microsoft 365 account (administrator) also shows the mode, the emergency accounts and `server_started_at` in `/api/m365/status`.

## Foundation for the next integrations (not built here)
SharePoint documents, Outlook mail, Teams notifications, approvals and Copilot/agents will use the **link** (per-user delegated tokens,
encrypted, refreshed by `ctx.m365Token(userId)`), never the sign-in, which stores no token. Each integration will add only the Graph
permissions it needs, in its own change, with consent; the sign-in scopes stay `openid profile email User.Read`.

## Rollback
- No code: `AUTH_MODE=hybrid` (or remove it) and restart → the password form is back for everyone (password sessions ended by the switch
  stay ended; people sign in again). `M365_ENABLED=0` also switches off Microsoft sign-in.
- Code: `git revert` the merge. `sessions.method` is an additive column and can stay (older code ignores it; Microsoft sessions then
  last the old 30 days again).
- Locked out (no Microsoft, emergency account lost): on the server PC set `AUTH_MODE=hybrid` in `.env`, restart, sign in with a password
  (`scripts/reset-2fa.js <user>` if the ERP code is lost).

# تكامل Microsoft 365 للأعمال / Microsoft 365 business integration (SharePoint · Outlook · Teams)

**بالعربي باختصار:** النظام يبقى المرجع للأرقام والضريبة والاعتمادات والصلاحيات. Microsoft 365 يستقبل **نسخاً**: ملفات PDF إلى
SharePoint (أوامر الشراء المعتمدة، العروض، الفواتير، العقود، مرفقات الموردين)، رسائل من بريد المستخدم نفسه في Outlook، وإشعارات
إلى قناة Teams. أي عطل في Microsoft لا يغيّر أي سجل في النظام. كل ميزة مطفأة حتى تُفعَّل في `.env`.

## Architecture
```
                ┌──────────────────────── Trigon ERP (system of record) ────────────────────────┐
 Browser ──────▶│ ACL + project scope + record state (approved PO, issued invoice…)             │
 (no tokens)    │   │                                                                            │
                │   ├─ modules/m365business.js ── lib/m365graph.js (fixed URLs, IDs validated,   │
                │   │      │                         timeouts, safe retries, safe errors)        │
                │   │      ├─ SharePoint ─ app token (client credentials, Sites.Selected) ──────┼──▶ graph.microsoft.com /drives/{drive}/root:/…:/content
                │   │      ├─ Outlook ─── user's delegated token (the Phase 1 link, Mail.Send) ─┼──▶ graph.microsoft.com /me/sendMail
                │   │      └─ Teams ───── channel webhook (Workflows), no Graph permission ─────┼──▶ *.logic.azure.com / *.webhook.office.com
                │   └─ tables: m365_documents (mapping), m365_mail_log, m365_teams_log           │
                └──────────────────────────────────────────────────────────────────────────────┘
 Entra ID: sign-in + MFA (Phase 1B / 1C / Microsoft-first). Approvals, numbers, totals, VAT, payroll, ledger: the ERP only.
```

## Settings (`.env`, all off by default)
| Variable | Meaning |
|---|---|
| `M365_SHAREPOINT_ENABLED=1` | switch SharePoint copies on |
| `M365_SHAREPOINT_SITE_ID` | site ID `host,guid,guid` (Graph: `GET /sites/{host}:/sites/{path}`) |
| `M365_SHAREPOINT_DRIVE_ID` | document library (drive) ID (`GET /sites/{site-id}/drives`) |
| `M365_SHAREPOINT_ROOT` | top folder, default `Trigon Civil Projects` |
| `M365_OUTLOOK_ENABLED=1` | users can send records from their own mailbox (each user reconnects once to grant Mail.Send) |
| `M365_TEAMS_WEBHOOK_URL` | the channel's Workflows webhook URL (**treat as a secret**: it carries a signature; shown nowhere) |
| `M365_TEAMS_INCLUDE_AMOUNTS=1` | allow amounts in Teams cards (only for a channel restricted to people who may see them); default: no amounts |
| `M365_TEAMS_EXTRA_HOSTS` | testing only: extra exact webhook host names (e.g. a local mock) |

Configuration changes are audited (`m365` / `config-change`, flags / names / host only).

## Graph permission matrix (least privilege)
| Feature | Graph permission | Type | Why | Admin consent |
|---|---|---|---|---|
| Sign-in, link, Check link | `openid profile email offline_access User.Read` | Delegated | identity + `/me` | User can consent (tenant policy may require admin) |
| SharePoint documents | **`Sites.Selected`** + a **write** grant on the Trigon site only | Application | upload / read the ERP's copies in one site; not `Sites.ReadWrite.All` (every site) | **Yes** (and a per-site grant by a SharePoint admin) |
| Outlook send | **`Mail.Send`** | Delegated | send as the signed-in, linked user from their own mailbox (`/me/sendMail`) | Usually user consent; admin consent if the tenant requires |
| Teams notifications | **none** (channel webhook via Teams Workflows) | — | posts a card to one channel; no Graph `ChannelMessage.Send` / `Teamwork.*` | No (the channel owner creates the workflow) |

Not used, on purpose: `Sites.ReadWrite.All`, `Files.ReadWrite.All`, `Mail.ReadWrite`, application `Mail.Send` (could send as anyone),
`ChannelMessage.Send`, `Group.ReadWrite.All`. (The older e-mail setting "Microsoft 365" in Settings → Email uses *application*
`Mail.Send`; prefer Outlook sending above, or restrict that app with an Exchange application access policy.)

## Entra configuration
1. Same app registration as Phase 1. **API permissions → Add**: Microsoft Graph → *Application* → `Sites.Selected` → **Grant admin
   consent**. If Outlook is used: Microsoft Graph → *Delegated* → `Mail.Send` (grant admin consent if your tenant blocks user consent).
2. Grant the app write access to the Trigon site only (a SharePoint / Global administrator, once), e.g. Graph Explorer (signed in as
   that administrator, with `Sites.FullControl.All` consented for Graph Explorer):
   `POST https://graph.microsoft.com/v1.0/sites/{site-id}/permissions`
   `{"roles":["write"],"grantedToIdentities":[{"application":{"id":"<client id>","displayName":"Trigon ERP"}}]}`
   (or PnP PowerShell `Grant-PnPAzureADAppSitePermission -AppId <client id> -DisplayName "Trigon ERP" -Site <site url> -Permissions Write`).
3. Conditional Access (MFA) as in the authentication sections applies to user sign-ins; the application token is protected by the client
   secret (rotate it before it expires; consider a certificate later).

## SharePoint setup
1. Create (or pick) a site, e.g. *Trigon Projects*, and a document library, e.g. *ERP Documents*. Access for staff is managed in SharePoint
   (site members / groups) — SharePoint permissions decide who reads the copies there; the ERP decides who may create them.
2. Find the IDs (Graph Explorer): `GET /sites/{tenant}.sharepoint.com:/sites/{site}` → `id`; `GET /sites/{id}/drives` → the library's `id`.
3. `.env`: `M365_SHAREPOINT_ENABLED=1`, `M365_SHAREPOINT_SITE_ID`, `M365_SHAREPOINT_DRIVE_ID` (optional `M365_SHAREPOINT_ROOT`); restart.
4. Settings → Microsoft 365 integration → **Test connection** (shows the site and library names).
Folders: `<root>/<project code - name>/<document type>/<number>.pdf` (created by the upload); supplier attachments:
`<root>/Suppliers/<supplier>/Supplier Documents/`. Project names are folder names only, never a security boundary.

**What is stored where:** `m365_documents` (entity, record, type, file name, site / drive / item ID, web link, SHA-256, size, status
`uploaded` / `failed` / `uploading`, error, attempts, who / when) — never a token. The PDF itself stays producible by the ERP;
SharePoint keeps versions when a record's copy is updated.

**Rules:** a purchase order is copied only when issued (sent / received / closed) and, if above the approval limit, approved; drafts and
cancelled orders are refused. Quotations: not drafts. Invoices / credit notes, subcontract agreements: any. Attachments: same rules as
the attachment itself. A copy is made by **Save to SharePoint** on the record (people who may edit that record); **Retry** after a failure;
**Update the copy** after a change (unchanged content is not sent again). An upload failure leaves the ERP record exactly as it was.

**Existing attachments:** `node --no-warnings scripts/m365-migrate.js` (dry run) → `--execute` after review. Resumable, skips what is
already there (same SHA-256), skips files above 4 MB (reported), never deletes, writes a JSON report in the data folder.

## Outlook setup
1. Entra: delegated `Mail.Send` (above). `.env`: `M365_OUTLOOK_ENABLED=1`; restart.
2. Each user who will send: Settings → Microsoft 365 account → **Disconnect**, then **Connect** (grants `Mail.Send`). Settings shows
   "You can send from your mailbox". **Test** reads the user's own mailbox address and sends nothing.
3. On a purchase order / RFQ / quotation / invoice: **Send via Outlook** → recipients (1–5, plus up to 5 in copy) → message. The PDF of that
   record is attached (or its SharePoint link if the PDF engine is unavailable). Sending the same record to the same recipients again
   within 7 days asks for confirmation. Every attempt is logged (`m365_mail_log`: recipients, subject, status, who, when) and audited.

## Teams setup
1. In the channel (e.g. *Procurement*): **⋯ → Workflows → "Post to a channel when a webhook request is received"** → name it *Trigon ERP*
   → copy the URL. (Office 365 "incoming webhook" connector URLs `*.webhook.office.com` also work while Microsoft supports them.)
2. `.env`: `M365_TEAMS_WEBHOOK_URL=<url>`; `M365_TEAMS_INCLUDE_AMOUNTS=1` only if the channel is restricted to people who may see amounts.
3. Settings → **Send a test notification**. Cards: *approval needed* (a PO spend approval is requested), *purchase order approved*, and
   *overdue purchase orders* (Settings → Send overdue purchase orders). Each has the number, project, supplier, the action and an
   **Open in Trigon ERP** link (to the registered address). Approving stays in the ERP (Spend approvals) with its own checks and audit.

## Failure model
| Situation | ERP behaviour |
|---|---|
| Microsoft / Graph unavailable, timeout | the action reports "Microsoft 365 is unavailable / did not answer"; GET / PUT retried twice; the ERP record unchanged; health shows the last error |
| Expired / revoked consent or secret | "access has expired or was revoked" — reconnect (user) / renew secret or consent (admin) |
| Insufficient permission (no Sites.Selected grant, no Mail.Send) | "does not have the permission …" / "reconnect to allow sending" |
| SharePoint unavailable / wrong site or library | upload marked **failed** with the reason; **Retry** later |
| Duplicate file | same record + type = same file, replaced (versioned); unchanged content not re-sent; concurrent uploads refused |
| Invalid folder / file name | names are sanitised (no `/ \ : * ? " < > | # %`, no `..`, no reserved names, length limits) |
| User unlinked / disabled | Outlook: "link your Microsoft account"; disabled users cannot sign in at all; uploads use the app, but only by authorised ERP users |
| Teams destination removed / invalid | "Teams did not accept the message" / "not a valid Microsoft webhook address"; logged; the ERP action already done |
| E-mail rejected | logged as failed with the reason; nothing in the ERP changes; send again after fixing |
Notifications run after the ERP action, never inside it: they cannot block or roll back an approval.

## Rollback
Switch the features off in `.env` (`M365_SHAREPOINT_ENABLED=0`, `M365_OUTLOOK_ENABLED=0`, remove `M365_TEAMS_WEBHOOK_URL`) and restart:
the buttons disappear, nothing calls Microsoft, ERP data are untouched. Code: `git revert` the merge; the three tables and the
`m365_connections.scopes` column are additive and can stay. Files already copied to SharePoint stay there (remove them in SharePoint if
wanted); revoke the site grant / `Sites.Selected` / `Mail.Send` in Entra if the integration should end.

## Troubleshooting
- *Test connection* says "does not have the permission": the site grant (step 2 of Entra configuration) is missing or for another site.
- "not found in Microsoft 365": wrong `M365_SHAREPOINT_SITE_ID` / `DRIVE_ID` (copy them again from Graph Explorer).
- Users cannot send: Outlook switched on? `Mail.Send` consented? the user reconnected after it was switched on?
- Teams test fails: the workflow was deleted / turned off, or the URL was copied incompletely.
- After changing `.env`: restart with the PID check (see *Restart that really applies .env*).

## Next phase: Copilot (architecture proposal, nothing indexed now)
**Recommended for this codebase: a secured ERP API / action layer used by a Copilot Studio agent (or a declarative agent with an API
plugin), not a Graph connector.** Why: ERP permissions are dynamic and record-level (roles, project scope, "site roles never see money",
payroll / HR privacy); an API answers **as the signed-in user** (Entra token → the same `tenant + oid` → ERP user → ERP ACL on every call),
so security trimming is exact and always current. A Graph connector copies data into the Microsoft index with static ACLs that would
have to mirror the ERP's rules and lag behind them.
- Identity: the agent calls the ERP with the user's Entra token (OAuth on-behalf-of); the ERP validates it like the sign-in (tenant, oid,
  audience, signature) and maps it to the linked ERP user; no service account with broad rights.
- Read-only first: project status, PO / RFQ status, delivery dates, supplier contacts, document links (SharePoint copies already carry
  SharePoint's own permissions and are indexed by Copilot through SharePoint itself).
- Never exposed / indexed: payroll, salaries, WPS, employee personal data, bank details / IBANs, VAT returns, the general ledger, audit
  logs, credentials. Amounts only to roles that see them in the ERP (`MONEY` roles), never to site roles.
- Writes (e.g. "approve PO 123") only as explicit actions that call the same ERP endpoints with the same checks and audit — Copilot never
  becomes the source of truth.
- A Graph connector is reasonable later only for non-sensitive, broadly readable reference data (e.g. the project list and their
  SharePoint folders), with ACLs set to an Entra group per project.
